The situation

Everything you are told is a claim.

  • The badge says passing.
  • The README says 182 tests.
  • The changelog says no known issues.
  • The package says 5 ports, byte-identical.

None of those is a fact. They are promises made by the thing that wants you to trust it.

Four ways a badge goes green without a single test running

Zero jobsA reusable workflow sat one folder too deep. The job count was zero — and the badge was still green.
Never wired to a pushIt ran on a timer. GitHub's own docs: with no run on your branch, the badge shows the most recent run across all branches.
The corpus was emptyA || true fallback wrote [] when generation failed. The comparison then agreed, perfectly, about nothing.

02 — the first lie5
The first a-ha

A badge is a claim.
A receipt is a fact.

A receipt says what ran, when, on what, and with what result — so that you can re-derive it yourself.

Every number in this deck has one. No receipt, no number.

131,499 boxes. one open.

03 — the boxes7
131,499 mutations, and not one of them was real

The suite was testing a copy.

A frozen fork of the code, months out of date, checked in beside the real thing. So:

  • It reported 14,611 disagreements that were not real — the copy was stale.
  • And the real code was never exercised at all. A bug in it would have been invisible, forever.

And the deepest part: the fix had already been made. Months earlier. On a branch. Never merged. So the report read like a live bug, and it was a fix that never landed.

You can only tell by watching it fail on purpose.

04 — break it12
So what do you actually buy?

A witness.

Every claim is recorded with a receipt, and the receipts are chained to each other, so you cannot quietly edit one without the chain noticing.

Re-derivableRun the same command on the same commit and you get the same bytes. Not "it was green" — here is the run, here is the hash, here is the command.
ChainedEach record carries the hash of the one before it. Change one, and everything after it stops verifying.

And a signed head, so the chain itself cannot be quietly rewritten either.

05 — the witness13
The hardest idea, told as a pair

You need a judge and a die.

The judge — readsGiven a document and a question, it returns how likely the answer is yes. It is smart, it is semantic, and it has opinions. We measured it preferring the first option 9 times out of 9, and a bad note in its memory could drag a true fact from 0.99 down to 0.60.
The die — does not readA quantum random number generator. It has no opinion — that is the entire point, and that is also its limit: a die cannot answer a question. It can only make sure the question was not arranged by somebody who wanted a particular answer.

Neither is enough alone. A judge alone can be steered. A die alone decides nothing.

05 — the witness14
And the trick that makes them work together

Ask twice. Keep only
what agrees.

Draw the order at random — and commit to it before asking, so nobody can choose the order that flatters them.

Then ask the same question in both orders.

  • Both orders give the same answer? That's a fact.
  • They disagree? Undecided. And that is a real answer.

We ran it: identical options came back UNDECIDED 6/6. Real options agreed 5/5 — and it picked the side we did not expect, which is how we knew it was reading and not just agreeing.

05 — the witness15
The third a-ha

"Undecided" is
a feature.

Almost every system has to answer. A gate has to pass or fail. A score has to be a number.

So a system that can say "I don't know, and here is why" is unusual — and it is the one that saves you.
